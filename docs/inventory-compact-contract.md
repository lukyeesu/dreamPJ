# Compact inventory contract — approved implementation direction

User direction: merge the inventory schema, Supabase Free only, no paid infrastructure. Both previous SQL scripts have already been run; treat their contents as real data. Previous UI features (mobile/tablet/theme, QR, helpers/teams, project work, cash) remain required.

## Physical tables: exactly 8 owned inventory tables

1. `inventory_categories` — existing categories; independent of handling type.
2. `inventory_items` — existing material/tool catalog and variants. Legacy banknote catalog records retained as historical data, never used as a second cash balance and never cached locally.
3. `asset_units` — existing stable `unit_code`, current serialized tool state.
4. `inventory_recipients` — staff/helper/team registry; merge team attributes here.
5. `inventory_documents` — typed business headers: issues, rounds, recovery, cash reservations/batches/prepared sets, work, submissions, inspections, incidents, legacy records, and audited commands.
6. `inventory_document_lines` — typed material/tool/output/receipt/inspection/cash/project-link lines.
7. `inventory_movements` — immutable stock/cash/tool/work audit events.
8. `cash_vault_denominations` — retain the existing five-row physical cash vault and its integer constraints, initialization and thresholds. Cash is isolated from the catalog cache.

Shared `projects`, `staff_users`, `roles`, `vendors`, `financial_transactions`, etc. are not inventory-owned and must not be dropped or duplicated. No permanent archive tables, private table forest, or one compatibility view per removed table. Temporary staging inside the migration is allowed. No fake data/counts.

Idempotency records merge into command/business document headers with unique request UUID, actor, action, payload hash and small response payload. Actual transaction documents can carry their own result; legacy requests lacking a business header use `COMMAND` documents. Preserve every old key, hash and response. Exclude technical command records from normal screens and realtime project streams.

## Canonical storage names (shared by all runtime authors)

Reuse existing column names where possible. Schema author may retain legacy columns to preserve data but all new runtime code uses this interface.

`inventory_recipients`: retain existing columns plus `staff_user_id TEXT UNIQUE`, `primary_recipient_id UUID`, `primary_receiver_name TEXT`, `member_names TEXT[]`, `team_is_active BOOLEAN`. Staff IDs may be UUID or TEXT in staff_users; compare as TEXT. Helpers do not require login accounts.

`asset_units`: retain existing columns plus `active_recipient_id UUID`, `active_custody_line_id UUID`, `active_round_id UUID`, `due_at TIMESTAMPTZ`. Active custody history is a TOOL_CUSTODY line; preserve old custody IDs as line IDs. Do not fabricate units for legacy quantity-only loans. Legacy borrowed units without a custody line remain explicitly adoptable/returnable.

`inventory_documents`: retain `id UUID`, `doc_number TEXT`, `doc_type TEXT`, `project_id TEXT`, `round_id UUID`, `recipient_id UUID`, `recipient_name_snapshot TEXT`, `team_members_snapshot TEXT[]`, `status TEXT`, `notes TEXT`, `actor_auth_user_id UUID`, `actor_name_snapshot TEXT`, `created_at`. Add `parent_document_id UUID`, `source_document_id UUID`, `title TEXT`, `due_at TIMESTAMPTZ`, `version INTEGER DEFAULT 1`, `is_cash BOOLEAN DEFAULT false`, `denomination INTEGER`, `metadata JSONB DEFAULT '{}'`, `updated_at`, `action_name TEXT`, `response_payload JSONB`. Existing `idempotency_key UUID` and `idempotency_payload_hash TEXT` are canonical. One document per request owns each key; if old issue headers and old request rows share a key, attach the cached result to that existing header rather than duplicate it. Unknown legacy keys get COMMAND headers. Doc numbers unique within doc_type, IDs globally unique; preserve original displayed codes. Project/history FKs RESTRICT, no silent cascading audit deletion.

Doc types: existing `PRODUCTION_ISSUE`, `FIELD_ISSUE`, `RETURN_UNUSED`, `RECOVERY`, `OPENING_STOCK`, `ADJUSTMENT`, plus `FIELD_ROUND`, `INCIDENT`, `CASH_RESERVATION`, `CASH_BATCH`, `CASH_PREPARED`, `WORK`, `SUBMISSION`, `INSPECTION`, `WORK_EVENT`, `COMMAND`, `LEGACY_LOAN`, `PROCUREMENT`, `DISPOSAL`, `CHECKLIST`, `SYSTEM_MIGRATION`. Keep status casing at the API expected by existing UI; work statuses are in_progress/submitted/completed/problem/cancelled. RPCs enforce per-type transitions. Cash-only WORK documents have is_cash=true and source_document_id pointing to their CASH_BATCH.

`inventory_document_lines`: `id UUID`, `document_id UUID`, `line_type TEXT`, `item_id UUID`, `unit_code TEXT`, `project_id TEXT`, `round_id UUID`, `source_line_id UUID`, `source_issue_movement_id UUID`, `description TEXT`, `unit TEXT`, `quantity NUMERIC(12,2) DEFAULT 0`, `required_qty NUMERIC(12,2) DEFAULT 0`, `submitted_qty`, `accepted_qty`, `rejected_qty`, `pending_qty`, `returned_qty`, `handed_over_qty`, `delivered_qty` (all NUMERIC(12,2), nonnegative), `denomination INTEGER`, `status TEXT`, `is_active BOOLEAN DEFAULT true`, `notes TEXT`, `metadata JSONB`, `created_at`, `updated_at`. Types: ITEM, TOOL_CUSTODY, ROUND_PROJECT, RECOVERY, WORK_OUTPUT, SUBMISSION, INSPECTION, CASH_RESERVATION, CASH_BATCH, CASH_PREPARED, CHECKLIST, LEGACY_DETAIL. Require integer cash counts and correct acceptance bounds; SUBMISSION pending=quantity-accepted-rejected. WORK_OUTPUT accepted+pending<=required. Cash batch issued=quantity, prepared=accepted_qty, returned raw=returned_qty, handed over=handed_over_qty. Prepared remaining=quantity-delivered_qty. Preserve every old output/submission/inspection/recovery/custody ID as a line ID. Foreign line updates must match assignment/document and positive expectedVersion.

`inventory_movements`: retain existing `id`, `document_id`, `item_id` (make nullable for cash/work events), `movement_type`, `quantity` (nonnegative; physical stock events positive, audit events may be zero), `delta_stock`, `source_issue_movement_id`, `source_item_variant_snapshot`, `notes`, `actor_auth_user_id`, `actor_name_snapshot`, `created_at`. Add `line_id UUID`, `unit_code TEXT`, `project_id TEXT`, `round_id UUID`, `recipient_id UUID`, `recipient_name_snapshot TEXT`, `denomination INTEGER`, `from_location TEXT`, `to_location TEXT`, `is_cash BOOLEAN`, `metadata JSONB`. Cash note_count maps to quantity, with original action retained as movement_type and full old fields preserved in metadata if not first-class. Old cash/stock/event IDs remain unchanged. No payroll deductions.

## Domain mapping and migration rules

Teams -> recipient columns. Field rounds -> FIELD_ROUND documents; round projects -> ROUND_PROJECT lines with real project FK. Material recoveries -> RECOVERY lines referencing original issue movement. Tool custody -> TOOL_CUSTODY lines + current unit columns, handover chain in metadata/events. Incidents -> INCIDENT headers/lines. Job reservations, helper batches, prepared sets -> typed cash headers/lines. Cash movements and work events -> inventory_movements. Production assignments/submissions/inspections -> WORK/SUBMISSION/INSPECTION headers; their child rows -> matching typed lines. Preserve source document/batch links. Legacy asset_loans/procurements/disposals/checklist items -> typed documents/lines with original IDs, codes, financial references and snapshots; never execute old stock triggers during import.

Full source records may be kept in target metadata when necessary for lossless migration; do not expose these snapshots in normal RPC responses. Prefer known columns plus leftover fields, not duplicated entire current payloads. No DELETE to reset real data. Validate per-source ID coverage/counts and material balances, per-denomination physical/reserved/held/prepared/delivered counts, active custody and accepted/submitted/pending output totals before old tables are removed. One transaction; unknown external dependencies abort before destructive DDL. Never use DROP CASCADE. Rollback must restore the original schema/data if any assertion fails. Rerun must preserve everything and create no duplicates. Support UUID/TEXT staff IDs and old scripts applied with no new operational data. Fresh install from shared base schema should also work without requiring the two large obsolete scripts.

## Runtime ownership and public contracts

Core runtime owns permission/anti-escalation helpers, warehouse_dispatch, metadata/stock/units/operations/cash/history/checklist reads and related core actions. Production runtime owns people resolution and all existing warehouse_* production RPCs; public API signatures stay compatible. Core dispatch can call an internal production helper for linked default work, and production issue wrapper can call core dispatch, but request UUID ownership must be atomic and never double-executed. Central request helper(s) belong to core; see follow-up service contract if exact helper needed.

Keep existing frontend warehouseService/productionService method signatures. Add bounded reads: `warehouse_list_stock(p_filters JSONB)` (default50, max100; server filters/search/counts/facets), `warehouse_list_units(p_filters JSONB)` (default20, max50; item_id/unit_code lookup), `warehouse_get_checklists(p_filters JSONB)` (default20), `warehouse_list_cash(p_filters JSONB)` (default20). Metadata warehouse_get_summary returns schema_version=2, bounded category/round metadata, counts, and first stock page only; asset units are loaded on demand. warehouse_get_operations defaults20 per selected section; history defaults20. Cash summary returns five denomination rows and first20 rows per section with has_more metadata.

Production board defaults25/max50 tasks, whole-project summary counts but bounded receipt previews; add `warehouse_get_work_details(p_assignment_id UUID,p_limit INT,p_offset INT)` and `warehouse_get_work_cards(p_project_id TEXT,p_assignment_ids UUID[])` (max25) to load details on demand and refresh only changed tasks. New cash inspection RPC `warehouse_inspect_production_cash(p_payload JSONB,p_idempotency_key UUID)` resolves a WORK cash assignment to its real batch and calls the canonical cash receipt exactly once; no REST query to removed production_assignments table. Generic work submit/inspect must never alter cash progress.

Realtime listens to current active project only, on inventory_documents filtered by project_id, excludes COMMAND records (their project_id should be NULL), uses parent/source IDs to refresh only changed work cards. Child changes must update their WORK header/version. No unbounded nested history in board responses. Cash RLS applies consistently to header, line and movement rows, including cash work/legacy request results. Revoke direct client DML, keep noncash catalog caching separate from all banknotes/cash. QR generation remains local.

## Shared helper contracts (core owner implements, production owner consumes)

Integration clarification: document lines also have `recipient_id UUID` and `due_at TIMESTAMPTZ`, preserving per-unit historical custody responsibility and return deadlines. These are columns on the same line table, not additional tables. The schema importer must populate them from old custody records. Do not introduce a second unsynchronized stock_quantity balance beside current_stock.

- `warehouse_command_lookup(p_action TEXT,p_hash TEXT,p_key UUID,p_is_cash BOOLEAN DEFAULT false) RETURNS JSONB`: auth/permission check, transaction advisory lock, validate stored action/hash/actor/cash permission, return cached response or NULL. Keep old hashes exactly: core uses fn_hash_action_payload; existing production wrappers may calculate their historical hash format. No RPC/physical writes while only looking up a new command.
- `warehouse_command_finish(p_action TEXT,p_hash TEXT,p_key UUID,p_response JSONB,p_document_id UUID DEFAULT NULL,p_is_cash BOOLEAN DEFAULT false) RETURNS JSONB`: persist result on that new semantic document or a COMMAND header. Never overwrite a document's DIFFERENT old request key; create a new COMMAND child if needed. Same-key core issue -> outer production wrapper may replace action/hash/response on that same issue header atomically, matching old behavior. Actor snapshots come from actual active staff.
- Helpers are private to definer functions: revoke EXECUTE from PUBLIC/anon/authenticated. Auth permission predicates used by RLS may remain executable.
- Production owner implements `warehouse_ensure_production_work(p_issue_document_id UUID) RETURNS UUID` and `warehouse_sync_cash_work(p_batch_document_id UUID) RETURNS VOID`. Core issue actions call the first for PRODUCTION_ISSUE after stock/tool writes; core cash actions call the second AFTER batch line updates (both source/target on handover). A default WORK output is 1 set, wrapper can replace it in the SAME transaction with explicit outputs. No physical stock/cash movement inside these production helpers. No duplicate cash counts.
- Install both runtime parts before any business command is executed. Schema import does not invoke these helpers or old stock/cash triggers.

## Build pieces (not standalone install scripts)

Schema/migration author owns `database_scripts/drafts/compact_schema.sql.part`; it establishes canonical 8 tables, lossless imports, validation and old-table retirement, with rerun handling. Core author owns `compact_core.sql.part`; production author owns `compact_production.sql.part`. Each part begins with a fail-closed guard requiring current_setting('flower.compact_build',true)='v2'. Do not run parts separately.

Final reviewed installer will concatenate BEGIN; SELECT set_config('flower.compact_build','v2',true); schema; core; production; COMMIT into ONE `database_scripts/inventory_compact.sql` after tests pass. Root will run tests against assembled local drafts in PGlite only, never a live Supabase database. User receives one ready installer with exact verification results. Previous scripts remain marked superseded snapshots for migration regression fixtures.

## Corrections to advisory reports

Table count does not itself increase connection pooling usage or egress. A separate vault does not guarantee zero egress or absolute privacy. Unbounded reads, duplicated boot downloads and repeated full-board reloads are the real network risks. Frontend changes ARE required for pagination, lazy units, old checklist writers, removed direct reads and realtime targets. The advisory audit's percentage/monthly usage figures are hypothetical, not measured and not a quota guarantee.
