# หน้ากลางงานผลิตและการตรวจรับตามโปรเจกต์

ผู้ใช้ขยายแผน C ให้มีหน้ากลางที่ทุกคนเห็นความคืบหน้างานเดียวกัน เช่น P-0001 ว่าใครรับผิดชอบอะไร ส่งแล้วเท่าไร ตรวจรับผ่านเท่าไร และยังขาดอะไร รวมชื่อที่มีในฐานข้อมูลเป็นตัวเลือกในฟอร์มผู้รับของและผู้รับผิดชอบ

## ขั้นตอนที่ต้องได้

1. เลือกโปรเจกต์และผู้รับผิดชอบจากรายชื่อพนักงาน/ผู้ช่วย/ทีมที่บันทึกไว้ ค้นหาชื่อได้และเพิ่มผู้ช่วยใหม่ได้โดยไม่ต้องมีบัญชีพนักงาน
2. เมื่อเบิกผลิต ระบุสิ่งที่ให้ไปใช้และสิ่งที่ต้องส่งกลับเป็นชิ้นงานแยกกัน ยืนยันครั้งเดียวสร้างใบเบิกและชุดงานผลิตที่เชื่อมกัน หากส่วนใดผิดพลาดต้องไม่เกิดรายการครึ่งหนึ่ง
3. งานเดียวมีผู้ช่วย 10 คนหรือมากกว่าได้ หน้ากลางแสดงรายบุคคลว่าได้รับมอบหมายอะไร จำนวนที่ต้องทำ ส่งแล้ว ผ่านตรวจ และยังขาด
4. ส่งงานบางส่วนหรือหลายครั้งได้ พนักงานผู้ตรวจเลือกจำนวนผ่าน/ไม่ผ่าน/รอแก้ไข บันทึกชื่อผู้ตรวจและเวลา การส่งมาถึงร้านยังไม่เท่ากับผ่านตรวจ
5. เมื่อผ่านตรวจครบ ผู้ตรวจยืนยันเสร็จสิ้นได้ คนอื่นเห็นสถานะใหม่ร่วมกัน แยกความพร้อมของชิ้นงานจากเครื่องมือค้างคืนและการส่งมอบลูกค้า
6. เพิ่มชุดงาน แก้รายละเอียด/กำหนดส่ง ปรับเพิ่มหรือลดจำนวนที่ยังไม่ผ่านตรวจ แบ่งงานที่เหลือให้คนอื่น หรือยกเลิกพร้อมเหตุผลได้ โดยไม่ลบประวัติรับของ/ส่งงาน/ตรวจรับที่เกิดแล้ว

## สถานะและยอด

- กำลังทำ: มีรายการที่ยังต้องทำหรือส่งเพิ่ม
- รอตรวจรับ: ส่งงานมาแล้วแต่ยังไม่ได้ตรวจครบ
- เสร็จสิ้น: ผ่านตรวจตามรายการที่ต้องส่งครบและพนักงานยืนยัน
- มีปัญหา: ระบุปัญหา ผู้รับผิดชอบแก้ไข และเหตุผลให้ทีมเห็น
- ยกเลิก: ยกเลิกงานที่เหลือพร้อมเหตุผล ประวัติที่ผ่านตรวจแล้วไม่หาย

แยกยอดสองอย่างให้ชัด: **ยังไม่ผ่านตรวจ** = จำนวนที่ต้องส่ง − จำนวนที่ผ่านตรวจ และ **ต้องส่งเพิ่ม/ส่งแก้ไข** = จำนวนที่ต้องส่ง − จำนวนที่ผ่านตรวจ − จำนวนที่ส่งแล้วรอตรวจ ไม่เรียกของที่มีมารอตรวจแล้วว่าเป็นของที่ยังไม่ส่ง ไม่หักยอดรอตรวจเป็นความสำเร็จ ไม่มีการรวมหน่วยต่างชนิดเป็นยอดเดียวที่สื่อผิด แสดงยอดรายรายการและสรุปจำนวนชุดงานที่ยังไม่ครบ

## กติกาที่ไม่ให้สต็อกหรือเงินจริงผิด

- การส่งงานและกดเสร็จสิ้นไม่ตัดวัสดุซ้ำ และไม่คืนเครื่องมือโดยอัตโนมัติ
- ยกเลิก/แบ่งงานไม่ทำให้เงินหรือของที่ผู้ช่วยถืออยู่หายไป ต้องบันทึกการคืนหรือส่งต่อของจริงแยกอย่างชัดเจน
- ธนบัตรที่พับหรือใส่ซองผ่านตรวจแล้วเป็นธนบัตรในชุดงาน ไม่ใช่เงินสดพร้อมเบิก การตรวจชุดเงินต้องเชื่อมรายการรับ prepared ที่มีอยู่และไม่เพิ่มเงินซ้ำ
- รายละเอียดชุดงานที่มีเงินจริงใช้สิทธิ์เงินสดเดิม หน้ากลางทั่วไปต้องไม่เปิดเผยยอดเงินจากการมีชื่อเป็นผู้ช่วย
- ทุกการส่งงาน ตรวจรับ เปลี่ยนสถานะ แก้จำนวน หรือแบ่งงานเก็บผู้ทำรายการและเวลา ป้องกันคำขอซ้ำ ตรวจยอดสะสมฝั่งเซิร์ฟเวอร์ และไม่รับยอดเกินรายการที่ส่งจริง
- การแก้ชื่อบุคคลในทะเบียนภายหลังไม่เปลี่ยนชื่อและผู้รับผิดชอบในประวัติเดิม

## รายชื่อจากฐานข้อมูล

แยกผู้ใช้งานที่ล็อกอินออกจากผู้รับผิดชอบงาน ตัวเลือกใช้ชื่อพนักงานที่เปิดใช้งานอยู่ใน staff_users รวมกับทะเบียนผู้ช่วยและทีม inventory_recipients โดยอ่านเฉพาะรหัส/ชื่อ/ชนิดที่จำเป็น ไม่ดึงข้อมูลบัตรประชาชน ที่อยู่ รหัสผ่าน หรือข้อมูลส่วนตัวที่ไม่จำเป็นมาใส่ dropdown

รายชื่อที่เลือกต้องอ้างอิงรหัสจริง ไม่ใช้ชื่อหรือรหัสจำลองแทน foreign key ชื่อคล้ายกันต้องแสดงชนิดหรือรหัสประกอบให้แยกได้ หลังเพิ่มผู้ช่วยแล้วต้องเลือกซ้ำได้หลัง reload

ข้อเข้ากันได้ที่ต้องตรวจ: ใน repo มีทั้ง schema พนักงานรหัส UUID และ migration ที่เปลี่ยน staff_users.id เป็นรหัสพนักงานชนิด TEXT ตัวเชื่อมรายชื่อต้องรองรับทั้งสองรูปแบบโดยไม่เปลี่ยนรหัสเดิมหรือสร้าง foreign key ที่ชนิดไม่ตรงกัน

สิทธิ์ที่อ้างอิงบทบาทต้องไม่ถูกยกระดับด้วยการแก้ role_id/auth_user_id ของตัวเองผ่าน policy เดิมที่เปิดกว้าง การเพิ่มส่วนงานนี้ต้องมีการตรวจและทดสอบป้องกันการเปลี่ยนสิทธิ์โดยพนักงานทั่วไป โดยยังรักษาการแก้ข้อมูลส่วนตัวที่ได้รับอนุญาต

## จอและธีม

หน้ากลางนี้อยู่ภายในคลังและเปิดจากโปรเจกต์ที่เลือกได้ ยังคง 4 เมนูหลักของแผน C โดยเป็นมุมมองงานผลิตภายในเบิก–คืนและทางลัดจากตะกร้า หน้าจอแคบใช้รายการตามคนและขยายรายละเอียด หน้าจอกว้างเทียบผู้รับผิดชอบหลายคนได้

รองรับการเปลี่ยนความกว้าง/สูงของหน้าต่างทั้งแนวตั้งและแนวนอน รวมแท็บเล็ต split view ใช้สีส่วนเน้นจาก theme variables เดิม สีสถานะยังสื่อความหมาย และต้องไม่ตีความการผ่านตรวจเป็นการหักเงินพนักงาน

## การเห็นความคืบหน้าร่วมกัน

ข้อมูลหลักอยู่ในฐานข้อมูลเดียวกัน รีโหลดหรือเปิดจากเครื่องอื่นต้องได้ข้อมูลล่าสุด เมื่อเปิดโปรเจกต์อยู่ใช้ realtime subscription ที่กรองโปรเจกต์และรวมเหตุการณ์ซ้ำก่อนดึงข้อมูล หยุด subscription เมื่อออกจากหน้า ไม่ใช้ polling หรือ effect ที่โหลดซ้ำตามอาร์เรย์ข้อมูล หาก realtime หลุดให้แสดงสถานะและปุ่มรีเฟรช

สถานะเอกสาร: ข้อกำหนดที่ผู้ใช้เพิ่มระหว่างพัฒนา ต้องทำและตรวจให้ครบก่อนรายงานแผน C เสร็จ
